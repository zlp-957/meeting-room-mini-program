# 会议室预约系统 需求分析与系统设计文档

## 第一章 引言

### 1.1 项目背景

随着企业规模的扩大和员工数量的增加，会议室资源的使用频率日益提升。传统的会议室管理方式（口头沟通、微信群接龙、纸质登记）存在诸多弊端：信息不透明、容易重复预订、无法追溯使用记录、管理员难以统一调度等。

为解决上述问题，本项目拟开发一套**企业内部会议室预约系统**，采用「微信小程序（用户端）+ Web 管理后台（管理员端）」的双端架构，实现会议室资源的数字化、流程化、透明化管理。

### 1.2 项目目标

1. 为普通员工提供便捷的会议室浏览、预约、取消、签到等自助服务；
2. 为管理员提供会议室、设备、预约审核、用户、公告、数据统计等后台管理能力；
3. 实现预约冲突自动检测，避免重复预订；
4. 沉淀预约使用数据，为会议室资源优化提供决策依据。

### 1.3 文档范围

本文档涵盖该系统的需求分析、系统总体设计、详细设计以及技术栈选型，作为项目开发的指导依据，验收通过后进入编码实现阶段。

### 1.4 术语定义

| 术语 | 说明 |
|------|------|
| 用户端 | 面向普通员工的微信小程序 |
| 管理员端 | 面向管理员的 Web 管理后台 |
| openid | 微信用户在特定小程序下的唯一标识 |
| 预约 | 用户对某一会议室在特定时间段的使用申请 |
| 审批 | 管理员对用户预约申请的通过/驳回操作 |
| 违约 | 预约后未按时签到，占用资源的行为 |

## 第三章 系统总体设计

### 3.1 总体架构

系统采用前后端分离架构，整体分为三层：

```
┌─────────────────┐   ┌──────────────────┐
│  微信小程序(用户) │   │  Web 管理端(Vue3) │
└────────┬────────┘   └────────┬─────────┘
         │      HTTPS/JSON     │
         └──────────┬──────────┘
                    ▼
        ┌───────────────────────┐
        │   Spring Boot 后端服务 │
        │  (Controller/Service/ │
        │   Mapper 三层结构)     │
        └───────────┬───────────┘
                    ▼
        ┌───────────────────────┐
        │     MySQL 8.0 数据库  │
        └───────────────────────┘
```

### 3.2 技术栈选型

| 层次 | 技术选型 | 说明 |
|------|---------|------|
| 用户端 | 微信小程序原生框架 | 直接对接微信登录、手机号组件 |
| 管理员端 | Vue3 + Vite + Element Plus + Axios | JavaScript，现代化前端 |
| 后端 | Spring Boot 2.7.x | 成熟稳定，生态完善 |
| ORM | MyBatis-Plus | 简化 CRUD，分页插件 |
| 数据库 | MySQL 8.0 | 关系型数据存储 |
| 鉴权 | Sa-Token | 轻量级权限认证框架，支持 token 会话 |
| 缓存 | Redis（可选） | 验证码、热点数据缓存 |
| 部署 | Nginx + 单体应用 | 前后端分离部署 |

**选型理由**：整体技术栈贴合主流企业内部系统开发实践，且与团队既有技能栈（Spring Boot + MyBatis-Plus + MySQL + Sa-Token）高度一致，降低开发与维护成本。管理员端选用 Vue3 而非 Vue2，兼顾技术先进性与长期维护性。

## 第四章 详细设计

### 4.1 微信小程序登录流程

登录采用「微信授权 + 手机号绑定」方案，核心流程如下：

```
1. 用户点击登录按钮，调用 wx.login() 获取临时 code
2. 前端将 code 发送至后端 /api/auth/login
3. 后端携带 code 调用微信 code2session 接口，换取 openid
4. 后端根据 openid 查询用户：
   - 已存在 → 直接签发 token
   - 不存在 → 返回"需绑定手机号"标识
5. 用户触发手机号授权，通过 <button open-type="getPhoneNumber">
   获取加密的 phoneCode
6. 前端将 phoneCode 发送至后端 /api/auth/bind-phone
7. 后端调用微信 getPhoneNumber 接口解密，得到手机号
8. 创建/更新用户记录，签发 Sa-Token 的 token
9. 后续请求均携带 token 进行鉴权
```

**关键点**：
- openid 作为用户唯一标识，天然防重复注册；
- 手机号由微信接口安全解密，后端拿到的是微信绑定手机号，用户无需手动输入；
- token 由 Sa-Token 统一管理，支持过期刷新。

### 4.2 预约核心业务流程

#### 4.2.1 预约流程

```
1. 用户选择会议室与时间段（起止时间）
2. 前端提交预约请求
3. 后端进行冲突检测：查询该会议室该时间段内
   是否存在"已通过"或"待审批"的预约记录
4. 无冲突 → 创建预约记录（状态=待审批/已通过，视规则而定）
   有冲突 → 返回冲突提示
5. 若需审批，管理员在后台审核通过/驳回
6. 预约通过后，用户按时签到使用
```

#### 4.2.2 时间冲突检测逻辑

冲突判定条件：同一会议室内，新预约时间区间与已有有效预约时间区间存在交集。

```
冲突条件：
new.start_time < existing.end_time AND new.end_time > existing.start_time
```

#### 4.2.3 取消与违约规则

- 用户在预约开始前可自行取消（如提前 2 小时）；
- 预约开始后未签到，标记为"违约"；
- 违约次数累计达到阈值（如 3 次），可限制预约权限。

### 4.4 权限设计

基于 Sa-Token 实现角色权限控制：

| 角色 | 可访问接口 | 权限说明 |
|------|-----------|---------|
| 普通用户 | /api/auth、/api/room、/api/booking、/api/announcement | 预约、查看 |
| 管理员 | /api/admin/** | 全部管理操作 |

- 小程序端通过 token 识别普通用户身份；
- Web 端通过 token 识别管理员身份，未登录或越权访问返回 401/403；
- Sa-Token 通过注解（如 `@SaCheckRole("admin")`）进行方法级权限校验。
